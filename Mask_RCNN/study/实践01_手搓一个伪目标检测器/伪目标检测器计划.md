按照系统数据流拆，整个问题是：

输入图片
↓
从图片提取信息
↓
找到可能有物体的位置
↓
对这些区域进一步分析
↓
判断类别和边界
↓
预测像素级 mask

拆成 6 个大任务。

| 任务            | 要解决的问题             |
| ------------- | ------------------ |
| T1 输入与 Tensor | 图片在程序里是什么          |
| T2 Backbone   | 怎么把图片变成 feature    |
| T3 RPN        | 怎么找到候选物体区域         |
| T4 RoIAlign   | 怎么从 feature 中取某个区域 |
| T5 Heads      | 怎么分类、回归、预测 mask    |
| T6 总流程        | 怎么把前面串起来           |

每个大任务继续拆

比如：

T1：输入与 Tensor

目标：

理解模型到底接收了什么。

拆成：

Python list
↓
Tensor
↓
shape
↓
索引
↓
切片
↓
[B, C, H, W]

T2：Backbone

问题：

一张 RGB 图片怎么变成特征？

拆成：

Conv2d
↓
feature map
↓
channel
↓
下采样
↓
ResNet stage
↓
C2 C3 C4 C5
↓
FPN
↓
P2 P3 P4 P5

每学一个东西都解决一个具体问题。

T3：RPN

问题：

模型怎么知道物体可能在哪里？

拆成：

Anchor
↓
IoU
↓
正负样本
↓
分类
↓
bbox regression
↓
decode
↓
NMS
↓
proposal

注意这里实际上又是一条小数据流。

6. 任务之间怎么联系

这个是你尤其要训练的。

不能只列：

Backbone
RPN
RoIAlign
Head

而应该永远写成：

输入 → 处理 → 输出 → 被谁使用

例如：

**Backbone**

输入：
image Tensor

处理：
卷积 / ResNet / FPN

输出：
feature maps

输出给：
RPN
RoIAlign

注意这里有一个重要联系：

                → RPN
features ───────
                → RoIAlign

所以 feature 不是“用了之后消失”。

它被多个下游模块共享。

---

RPN

输入：
features

处理：
anchor + objectness + bbox regression + NMS

输出：
proposals

输出给：
RoIAlign / RoI Heads

---

RoIAlign

输入实际上是两个来源：

features ──────┐
               ↓
             RoIAlign
               ↑
proposals ─────┘

这是非常关键的“模块关系”。

因为：

features 告诉它：图像内容在哪里
proposals 告诉它：我要看哪个区域

最终：

features + proposals
↓
RoIAlign
↓
固定尺寸 RoI feature

所以完整依赖关系应该这样画：

```
                    image
                      │
                      ▼
                  Backbone
                      │
                      ▼
                   features
                  /        \
                 /          \
                ▼            │
               RPN           │
                │            │
                ▼            │
            proposals        │
                │            │
                └─────┬──────┘
                      ▼
                  RoIAlign
                      │
                      ▼
                roi_features
                 /    |    \
                /     |     \
               ▼      ▼      ▼
           class    bbox    mask
            head     head    head
               \      |      /
                \     |     /
                 ▼    ▼    ▼
                   result
```

以后分析任何模型都应该试着画这个图。

关键的是“为什么这样拆”

我们给任务拆解设置一个规则：

一个子任务只解决一个核心问题。

例如不能设置：

学习 RPN。

这个太大。

应该变成：

1. anchor 是什么？
2. anchor 怎么生成？
3. 怎么判断 anchor 好不好？
4. IoU 怎么算？
5. 怎么分正负样本？
6. RPN 怎么预测前景概率？
7. bbox 偏移量是什么？
8. 怎么从偏移恢复 box？
9. 为什么需要 NMS？
10. 最终怎么得到 proposals？

这样每完成一步都有明确结果。

任务树:

```
最终目标
独立理解 + 手写 Mask R-CNN
│
├── A. 代码阅读基础
│   ├── Python
│   ├── class
│   ├── function
│   └── import
│
├── B. Tensor 基础
│   ├── shape
│   ├── indexing
│   ├── broadcasting
│   └── tensor operation
│
├── C. Backbone
│   ├── Conv
│   ├── ResNet
│   └── FPN
│
├── D. RPN
│   ├── Anchor
│   ├── IoU
│   ├── bbox regression
│   └── NMS
│
├── E. RoI
│   └── RoIAlign
│
├── F. Heads
│   ├── classification
│   ├── bbox
│   └── mask
│
└── G. Integration
    ├── forward
    ├── loss
    ├── training
    └── inference
```

**一次只能沿一条分支往下走**。

你现在实际上就在：

```
A 代码阅读基础
+
B Tensor基础
↓
为 C/D/E/F 铺路
```

这也是为什么目前先写 SimpleMaskRCNN 是有意义的：它不是为了模拟算法，而是让你先把系统骨架和模块依赖关系建立起来。
